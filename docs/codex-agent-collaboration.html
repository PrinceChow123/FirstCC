CODEX AGENT ATLAS

子 Agent 与跨工作区协作

给需要在多个 Codex 环境之间协作、交接和复核的工程实践手册。

标注约定：已记录的 Codex 行为 表示关于会话、配置或运行环境的事实说明；推荐工作流 表示本手册建议采用的工程做法。两类内容不会互相替代。

01. 快速结论

推荐工作流 不要复制 Agent A，而要调用一个真正运行在 A 环境中的 Codex 实例。

已记录的 Codex 行为 对话上下文独立，项目文件环境通常共享。一个名字、一个角色提示或一个子 Agent 标签，都不会把另一个工作区的项目说明、工具配置和会话自动装入当前 Agent。

推荐工作流 把 B 设为协调者：B 分解任务、调用 A、验证结果并决定是否返工；A 在自己的工作目录、项目说明和必要的全局状态下完成执行。

02. Agent 与会话

已记录的 Codex 行为 Agent 是角色和运行环境的组合：有效工作目录、项目 AGENTS.md、配置、技能、权限和可用工具共同决定它如何工作。会话则是一条可续传的对话线程，保存此前的消息和该线程的任务脉络。

已记录的 Codex 行为 不能把“我是 Agent A”理解为“我已经进入 A 的环境”。同一个角色可在多个线程中运行；同一个线程也不会因为改名而迁移到另一工作区。

角色配置
定义执行时可用的环境与规则。
会话线程
以 threadId 标识，用于在同一对话脉络上继续追问。
工作区
项目文件、项目级指令和通常的版本控制边界所在位置。

03. 子 Agent 上下文

已记录的 Codex 行为 普通子 Agent 使用独立的 Agent 线程与上下文窗口。父 Agent 可在启动时传递任务、背景和验收条件，但子 Agent 不会自动看到父线程的全部逐字记录；同级子 Agent 之间也彼此隔离。

已记录的 Codex 行为 这不等于文件系统一定隔离：在同一 checkout 中运行的多个 Agent 可能读写同一项目文件。共享文件访问不能推导出共享对话上下文，反之亦然。并发修改同一文件仍会产生覆盖或合并冲突。

推荐工作流 启动子 Agent 时，把它完成任务所必需的上下文显式写入任务说明，包括目标、文件范围、禁止事项、验证命令和回传格式。

05. 跨工作区协作

推荐工作流 选择结构前先分清：谁拥有最终决策、谁能写哪些文件、以及结果如何被复核。

推荐工作流 按任务边界选择协作模式
模式适用场景优点风险与补偿
共享父工作区小任务、同一项目交接成本低写入冲突高；分配互斥文件范围。
独立会话、人工转述探索或人工审查边界清晰、启动简单信息可能丢失；使用结构化交接合同。
自动协调者调用执行者可重复的跨工作区任务B 可复核、返工并保留 A 的环境需配置 MCP、超时和信任边界；这是推荐模式。

已记录的 Codex 行为 只创建新会话不能隔离磁盘写入。推荐工作流 若需要真正隔离文件改动，请使用不同 checkout（例如 worktree）。

06. Agent B 指挥 Agent A

推荐工作流 B 是监督者，A 是在独立环境中执行的 Codex 实例。B 不复制 A 的配置；B 通过 A 的 MCP 服务发送有边界的任务并读取回传。

cwd选择项目上下文、项目指令与文件作用域
CODEX_HOME选择配置、技能与 memories 等全局状态
threadId标识会话线程，承接同一任务的定向反馈

推荐工作流 将任务闭环执行为：

  1. B 分解任务，明确 A 的文件范围与验收标准。
  2. B 调用 codex(prompt, cwd=A)，A 执行并回传内容和 threadId。
  3. B 验证结果；需要调整时用 codex-reply(threadId, feedback) 定向返工。
  4. B 接受合格输出并集成，保留验证证据。
# B 的监督者职责

将 Agent A 视为独立执行环境：不要假设 A 继承 B 的项目配置或旧会话。
每次委派须给出目标、文件范围、禁止事项、验收命令和回传合同。
先验证 A 的 deliverables 与 verification；未达标时只用 threadId 发出有界反馈。
不得把凭据、令牌、二维码或不必要的私人上下文放进任务提示。

07. MCP 配置

推荐工作流 在 B 的 .codex/config.toml 中注册 A 的 MCP 服务。先用基线配置选择 A 的项目环境；它不设置 CODEX_HOME，因此不提供持久 memory 隔离。

[mcp_servers.agent_a]
command = "codex"
args = ["mcp-server"]
cwd = "/absolute/path/to/workspace-A"
startup_timeout_sec = 20
tool_timeout_sec = 3600
required = true

推荐工作流 需要将 A 的持久记忆、用户级配置与 B 隔离时，使用下面的独立 CODEX_HOME 变体。占位目录必须事先存在，并有意配置好 A 实际需要的 config、认证与 skills；不要盲目复制 B 的全部状态，也不要把凭据写入本页或版本库。

[mcp_servers.agent_a]
command = "codex"
args = ["mcp-server"]
cwd = "/absolute/path/to/workspace-A"
env = { CODEX_HOME = "/absolute/path/to/codex-home-A" }
startup_timeout_sec = 20
tool_timeout_sec = 3600
required = true

已记录的 Codex 行为 cwd 选择 A 的项目环境；CODEX_HOME 选择 A 的全局状态（包括本地 memories 的位置）。两者负责不同维度，不能相互替代。独立进程如果共享同一 CODEX_HOME，持久 memories 仍然共享。

codex({
  prompt: "在 workspace-A 中实现已批准的任务；只修改任务合同列出的文件，并回传结果合同。",
  cwd: "/absolute/path/to/workspace-A",
  sandbox: "workspace-write",
  "approval-policy": "on-request"
})

推荐工作流 选择最小必要权限，并在 B 中限制工具暴露。已记录的 Codex 行为 即使审批策略为 never，它也只是改变审批行为，绝不增加 sandbox 或系统权限。

08. 线程续传

已记录的 Codex 行为 首次 codex 调用创建 A 的会话并返回 threadId。推荐工作流 将该标识与任务合同一起保存；B 对同一任务的后续反馈用 codex-reply 发回相同线程，从而保留该次执行的对话脉络。

已记录的 Codex 行为 cwd 决定项目上下文，CODEX_HOME 决定全局状态，threadId 决定会话续传。其中任何一个都不能替代另外两个。持久配置或 memory 可以影响未来启动，但它们不是一条旧对话 transcript。

codex-reply({
  threadId: "returned-thread-id",
  prompt: "验收未通过：请仅修复第 2 项，重新运行 npm test，并按结果合同回传。"
})
何时不要续传旧线程？

推荐工作流 当任务目标、权限范围或受信任项目发生实质变化时，创建新任务和新线程更可审计；不要借助旧上下文绕过新的边界。

09. 交接与验收

推荐工作流 交接应是结构化接口，不是“完成了”的一句话。B 先给 A 任务合同，再根据结果合同验收；返工也必须带范围，避免一次反馈扩张成无边界重做。

任务：<明确目标>
工作目录：/absolute/path/to/workspace-A
允许修改：<文件或目录列表>
禁止修改：<边界列表>
验收：<命令与预期结果>
回传：按结果合同提供状态、交付物、验证、阻塞项和下一步。
status: DONE | DONE_WITH_CONCERNS | BLOCKED
deliverables:
  - <变更的文件或产物>
verification:
  - command: <执行过的命令>
    result: <精确结果>
blockers:
  - <无则写 none>
next_action: <B 应执行的下一步>

推荐工作流 验收顺序：检查文件范围与提交差异；运行合同中的验证；审阅风险和阻塞项；仅对未达标项发送 threadId 返工；最后再由 B 集成已接受输出。

10. 安全检查

推荐工作流 将下列项目作为每次委派和集成前的检查清单：

  • 为每个执行者指定最小权限、明确 cwd 和可写文件范围。
  • 不在配置、提示、日志或交接物中放入凭据、令牌、二维码或机器专属秘密。
  • 同一 checkout 的并发写入要么串行化，要么按互斥文件范围拆分；需要隔离时使用独立 worktree。
  • 不要把共享文件系统误解成共享 memories 或共享对话；检查 CODEX_HOME 是否需要隔离。
  • 把 MCP 服务、项目指令和外部工具视为信任边界；只连接可信配置并审阅其权限。
  • 设置启动与工具超时，记录 threadId、命令和验证结果，避免静默卡住或不可追溯的返工。
  • 接受输出前独立验证；A 的“完成”是待验证结果，不是 B 的最终结论。
